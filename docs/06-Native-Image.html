GraalVM Native Image

Coffi works under GraalVM native-image (GraalVM for JDK 25+, where FFM support is enabled by default; downcalls and upcalls are supported on Linux/x64, Windows/x64, macOS/AArch64, and Linux/AArch64). A complete working example lives in examples/native-image/ in the coffi repository, buildable in a container with Dockerfile.native:

docker build -f Dockerfile.native -t coffi-native .
docker run --rm coffi-native

Native image imposes two constraints that shape how coffi is used: classes cannot be defined at runtime, and native state (addresses, downcall handles, loaded libraries) cannot be baked into the image at build time. Coffi detects the image build (via the org.graalvm.nativeimage.imagecode property) and splits its work accordingly: wrapper classes are generated at build time and baked in, while symbol resolution and downcall handle creation are deferred until the image runs.

The rules

  1. Define fns at the top level; load libraries in -main. Top-level defcfn forms run at image build time, which is what generates and bakes the wrapper classes for their signatures — including classes for any [::ffi/fn ...] callback types they mention. load-library must run at image runtime (e.g. in -main); at the top level of a namespace it would execute during the image build and its state would be discarded. Consequently a missing symbol throws UnsatisfiedLinkError at first call rather than at defcfn time.

  2. Creating fns with new signatures at image runtime does not work. cfn/make-downcall at runtime is fine when the same argument/return shape was already used somewhere at build time (the generated classes are memoized per shape); a shape never seen at build time needs runtime class definition and fails.

  3. AOT-compile everything, and give native-image only classes and jars. If .clj sources are on the image classpath, Clojure may recompile them at runtime, which native-image forbids. examples/native-image/build.sh shows the classpath construction.

  4. Use build-time initialization for Clojure. Add com.github.clj-easy/graal-build-time to the dependencies and pass --features=clj_easy.graal_build_time.InitClojureClasses. Namespaces must not live in the default package (use hello.core, not hello). Also pass --initialize-at-build-time=org.objectweb.asm — coffi’s bytecode generator (insn) uses ASM at build time.

  5. Register the FFM descriptors — coffi generates them for you. Every function descriptor used for a downcall or upcall must be in the image’s reachability metadata. Coffi records every descriptor when a fn is constructed, so requiring the namespaces on a JVM and calling coffi.ffi/write-native-image-metadata! is enough — nothing needs to execute:

clojure -J--enable-native-access=ALL-UNNAMED -M -e \
  "(require 'my.main) (coffi.ffi/write-native-image-metadata! \"coffi-config\")"
native-image ... -H:ConfigurationFileDirectories=coffi-config

This includes callback (::ffi/fn) descriptors that the native-image tracing agent only records when a callback actually fires during a traced run. Use the agent instead of (or alongside) coffi’s generator when your program also needs reflection/resource/JNI metadata, or creates FFM handles outside coffi — multiple config directories can be passed to -H:ConfigurationFileDirectories, comma-separated.

  1. Pass --enable-native-access=ALL-UNNAMED both to the agent run and to native-image.

Performance

By default, native FFI calls cost microseconds, not nanoseconds: downcall invocation through a runtime-created handle is unoptimized in native image (an open GraalVM task, oracle/graal#8113) — every call goes through interpreted method-handle dispatch, and this applies to plain-Java static-final handles just the same as coffi’s fns.

On GraalVM 25.1 and newer there is a fast path, and coffi supports it. Unbound downcall handles (no target address — the address is passed per call, which is coffi’s architecture) may be created at image build time; a baked handle is a compile-time constant, so invokeExact intrinsifies into a direct call to the AOT-generated stub. Opt in on the native-image command line:

native-image ... -J-Dcoffi.ffi.eager-native-image-handles=true

This took the benchmark from ~4 µs to ~300 ns per call (~230 ns with PGO). GraalVM 25.0 and older fail the image build with this enabled, which is why it is opt-in. Note that bound handles — including those generated by jextract — cannot take this path and remain at microseconds.

Raw C compute and bulk segment copies run at full speed in all configurations. For chatty per-call-latency-sensitive workloads on GraalVM older than 25.1, prefer coarse-grained calls or the JVM.

Everything around the calls is very tunable, and the defaults undersell native image:

  • Edition and GC matter far more than -O flags. -O3 -march=native measured no change, while Oracle GraalVM with --gc=G1 made the allocation-heavy benchmark faster than the JVM (Serial GC, the community-edition default, was ~6x slower).
  • Profile-guided optimization (Oracle GraalVM) closed the pure-Clojure compute gap from ~6.6x to ~1.2x. Dump each profiling run to its own file and merge them (--pgo=a.iprof,b.iprof): a partial profile marks unprofiled hot paths as cold and makes them slower than no PGO at all.
  • Deep recursion needs stack headroom: frame sizes vary by edition and GC, so pin -R:StackSize (image) and -Xss (JVM comparison runs) rather than trusting defaults near the cliff.

See the benchmarks section of the README for all numbers, and examples/benchmarks/build.sh for a harness with these knobs wired up (BASE_IMAGE, EXTRA_NATIVE_OPTS, PGO=1).

What doesn’t carry over

  • Library reloading (load-library on a changed file, unload-library) works mechanically in an image, but the REPL workflow it exists for does not apply; treat it as untested there.
  • Deserializing function pointers (::ffi/fn as a return or field type) creates a bound downcall handle at runtime; its descriptor must have been registered (the agent records it if the code path ran during the agent run).
